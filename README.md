# Stringee iOS SDK Samples

This repository contains sample iOS apps for the Stringee SDK.

## StringeeCallSample

`StringeeCallSample` is the SPM-based UIKit sample. It uses:

- Swift Package Manager dependency: `https://github.com/stringeecom/Stringee-iOS-SDK-SPM.git`
- Exact SDK version: `2.0.3`
- UIKit with programmatic Auto Layout
- MVVM plus service protocols
- No `Main.storyboard` or XIB for the app UI

Equivalent `Package.swift` dependency:

```swift
.package(
    url: "https://github.com/stringeecom/Stringee-iOS-SDK-SPM.git",
    exact: "2.0.3"
)
```

The sample demonstrates app-to-app calls with foreground UI, CallKit, and PushKit:

- Connect to Stringee with an access token
- Start a voice call with `StringeeCall`
- Start a video call with `StringeeCall2`
- Receive foreground incoming calls
- Receive VoIP push notifications for background/killed-state incoming calls
- Report incoming calls through CallKit
- Answer, reject, hang up, mute, speaker, and camera toggle

## Access Token

Enter a Stringee access token in the app at runtime. Do not commit real access tokens or API secrets to the repository.

Access tokens should be generated by your backend using your Stringee API credentials, then passed to the sample app for testing.

For the CallKit/PushKit sample flow, the app stores the last entered access token in Keychain so it can reconnect to Stringee after a VoIP push wakes a killed or suspended app. This is demo behavior. A production app should fetch or refresh short-lived client tokens from your backend and must never embed API secrets in the iOS app.

## CallKit and PushKit

The sample registers a VoIP push token with Stringee using:

- `isVoip: true`
- `isProduction: false` for Debug builds
- `isProduction: true` for Release builds

To test real background or killed-state incoming calls:

1. Use a physical iPhone. VoIP push cannot be validated end-to-end on the simulator.
2. Use an Apple Developer account with Push Notifications enabled for the app bundle ID.
3. Configure Background Modes with Voice over IP.
4. Configure APNs Auth Key/certificate information in the Stringee dashboard for the same bundle ID and environment.
5. Run the app once, connect with a valid Stringee access token, and confirm the VoIP token registration log.
6. Kill or background the app, then call that Stringee user from another client.

Push payloads are parsed from Stringee `CALL_EVENT` notifications. The app reports CallKit immediately, reconnects Stringee if needed, waits for the matching SDK incoming-call callback, then answers/rejects/hangs up through the Stringee session. Incoming sessions call `initAnswer()` before `answer()`.

## Running

Open:

```sh
StringeeCallSample/StringeeCallSample.xcodeproj
```

Select the `StringeeCallSample` scheme and run on a device or simulator. Xcode will resolve the Stringee package automatically from SPM.

For command-line verification:

```sh
xcodebuild \
  -project StringeeCallSample/StringeeCallSample.xcodeproj \
  -scheme StringeeCallSample \
  -destination 'platform=iOS Simulator,name=<available iPhone simulator>' \
  test \
  CODE_SIGNING_ALLOWED=NO
```

## Limitations

Automated tests use fake CallKit/PushKit services on the simulator. Real VoIP push delivery, APNs environment matching, and killed-state behavior must be verified on a physical device with the correct provisioning profile and Stringee dashboard configuration.
